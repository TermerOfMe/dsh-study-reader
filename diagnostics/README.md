# 1.13.0 连续页卡顿调查（2026-11-11）

## 范围与结论

在现有 DSH Desktop 窗口、实际 `dsh-app://app/` 页面中调查《强化学习.pdf》（172,338,016 字节，189 页），未修改阅读器实现、版本、安装配置或默认设置。基线为提交 `05c955a` / 1.13.0。诊断中临时加入性能观察器与 API 计时，并进行了临时 DOM/CSS 对照；两条被排除的 CSS 规则在 `finally` 中恢复。调查后通过关闭开发者工具、刷新现有页面清除临时探针。

已证实的主要阻塞链是：文字层逐项写入已连接的 DOM → PDF.js 在连接到 document.body 的隐藏 canvas 上设置字体/测量字宽 → 反复触发同步样式更新 → 当前 DSH 页面中的全局 CSS 放大更新成本 → 连续页多个文字层串行占满主线程。图片已经显示并不代表文字层已经完成。

这不是用无头浏览器推断的结论。此前无头测试未包含真实 DSH 全局 CSS，不能用于证明现有桌面界面流畅。

## 实际窗口测量

开发者工具开启、临时计时探针开启；绝对数值不是未来版本的性能承诺。对照在同一运行环境中完成。

| 实验 | 结果 |
| --- | --- |
| 单页第 2 页 | 图像请求 6ms；drawImage 不足 1ms；文字层 707ms；对应主线程长任务 706ms |
| 单页第 3 页 | 图像请求 5ms；drawImage 不足 1ms；文字层 573ms |
| 第 3 页的文字层内部 | 36 次 measureText 合计 413ms；11 次 font 设置合计 152ms；占 573ms 的绝大部分 |
| 在第 3 页切换连续页，激活第 1–5 页 | 五个文字层分别 1098 / 1675 / 274 / 8355 / 12045ms，总计约 23.4 秒 |
| 同一次连续页实验内部计时 | 418 次 measureText 合计 11.42 秒；215 次 font 设置合计 11.88 秒 |
| 同一次连续页的位置读取 | getBoundingClientRect 19 次，合计 49ms；不是此次数秒长任务的主因 |
| 同一内容、135 个文字 span，文字层直接连接到页面 | 1843ms |
| 同一内容、135 个文字 span，文字层在脱离文档的临时容器构建 | 68ms；约快 27 倍。仅验证构建阶段，尚未验证正式接入后的选择定位与完整交互 |

附加微实验：每次插入一个临时文字节点，再设置测量字体、测量文字，循环 12 次。连接到 body 的 canvas 字体设置耗时 567ms；未连接的 canvas 与 OffscreenCanvas 对照均不足 1ms（四舍五入为 0）。无 DOM 写入时连接 canvas 的同类实验为 109ms。证明成本与 DOM 样式更新耦合，而不只是字体本身或 PDF 内容解析。

## 全局 CSS 放大因素

当前运行界面存在两条未限定宿主类名的选择器：

```css
:has(> ._4EiRdG_navigator._4EiRdG_fill) > :not(._4EiRdG_navigator)
:has(> ._4EiRdG_navigator:not(._4EiRdG_wholePage)) > :not(._4EiRdG_navigator)
```

同一个 12 次测量实验，保留规则为 566ms，临时排除这两条规则为 107ms，随后恢复原规则。证实这两条规则显著放大成本，但不能据此断言它们是所有样式开销的唯一来源；尚未将这两条运行时规则归属到具体发行包。

## PDFium 与回退提示

- HTTP `/bootstrap` 确认版本为 1.13.0。
- 实际 Electron 页面内请求第 95 页，返回 200、`image/jpeg`、555,366 字节、`x-page-width:1599`、`x-page-height:2260`；自定义协议保留了图像尺寸头。
- 服务端三组各五页、2384px 请求均成功：组完成约 0.8–1.9 秒，组内普通 bootstrap 请求也被拖延约 0.9–1.95 秒。PDFium/WASM、像素复制和 JPEG 编码仍占 Host 事件循环，这是独立的次要问题。
- 实际连续页卡顿实验中，所有页面图请求均为 200，显示 PDFium，捕获的阅读器 warning 数量为 0。因此严重卡顿在没有 PDF.js 画布回退时同样成立。
- 用户此前看到的回退错误本次未复现，不能给出原始异常的确定原因。现有代码把任何页面图获取失败都变为 null，然后启用 PDF.js 画布回退；界面的“请确认重启”是统一提示，不能用它判定用户未重启。见 [client.js](../client.js#L1367) 与 [警告显示](../client.js#L3726)。

## 代码中另外确认的开销

- `distance: number - pageNumber` 使每次跨页时所有 189 个 ContinuousPage 的浅比较失败，是 1.13.0 新增开销；不等于所有页面都重画像素。见 [页面列表](../client.js#L3259)。
- 每次滚动帧从第一页顺序读取位置，复杂度随当前页增加。见 [滚动处理](../client.js#L3168)。
- 后台提取完成替换 doc 对象会触发全部页面组件重新执行；宽度变化会重启活动页面渲染。
- 以上可以优化，但本次字体计时已经解释了主要数秒长任务，不应再将预取窗口/React 重渲染当成唯一根因。
- 返回对话曾安排独立测量，但没有取得可靠的完整输出，因此不对它剩余的独立延迟给出已证实的归因。

## 供用户权衡的方案（尚未实施）

1. **保留主页面与文字选择，调整文字层构建方式。** 在脱离文档的容器中建立文字层，再一次性装入；分页调度、取消、邻页缓存保持完整，并清除 distance 导致的全列表重复执行。已有 1843→68ms 的机制对照支持。必须验证文字选区、缩放、跳转和重新进入邻页，不能把该微实验当作已完成的修复。
2. **将阅读器放入独立 iframe，隔离全局样式。** 保持 DSH 内阅读，但需桥接选区、翻译与问答。iframe 隔离 DOM/CSS 不保证拥有独立线程，仍需处理长任务。改动和回归面更大。
3. **独立阅读窗口/独立渲染进程。** 可更强地隔离主对话的响应，但会改变使用流程，需要设计窗口间文档、选区和问答同步。新窗口是否真正独立进程必须验证，不能仅凭 window.open 推断。

仅将相同 DOM 从主页面移到侧栏不会隔离主线程和全局 CSS，不是本次根因的针对性修复。建议先选方案 1；如希望长期隔离其他插件 CSS，再考虑方案 2。Host PDFium 的 worker 化应作为单独改动评估。
